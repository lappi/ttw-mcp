# ttw-mcp — дизайн

Дата: 2026-09-22
Статус: утверждён к реализации

## 1. Цель

MCP-сервер, дающий AI доступ к данным рейтинга настольного тенниса
r.ttw.ru: игроки, их матчи, очные противостояния, турниры.

Сервер — **тонкая прослойка получения данных**. Он не считает аналитику,
не хранит состояние и не кэширует. Всю интерпретацию — форму игрока,
удобных соперников, тренды, разведку турнира — делает AI над JSON,
который сервер отдаёт.

### Сценарии, которые должны стать возможны

1. Своя форма и динамика: где теряется рейтинг, как менялся за период.
2. Подготовка к сопернику: его форма, очные встречи, общие соперники.
3. Разведка турнира: состав участников, расклад по рейтингам, итоги.

## 2. Что выяснено об источнике

Разведка проведена 2026-09-22 на живом сайте. Факты ниже — основание
для решений в разделах 4–7.

### Платформа

WordPress 4.8.25 на PHP 5.6.40, nginx, IP 109.95.210.8. Данные рейтинга
лежат не в WordPress, а в собственных таблицах темы `ttw-rating`, и
рендерятся сервером в HTML.

### Публичного API нет

`/wp-json/` открыт, но содержит только ядерные namespace (`wp/v2`,
`oembed/1.0`) и только типы `post`, `page`, `attachment`. Игроков и
турниров там нет.

Есть три недокументированных `admin-ajax` действия (найдены в
`wp-content/themes/ttw-rating/js/main.js`), работающих без авторизации и
без nonce, все `POST` на `/wp-admin/admin-ajax.php`:

| action | параметры | ответ |
| --- | --- | --- |
| `get_players_by_name` | `name`, опц. `id` | HTML-список `<div><a href="/players/?id=…">ФИО</a></div>` |
| `get_player_points` | `id` | CSV-строка `год,месяц,день,рейтинг;…` |
| `get_tournaments_by_name` | `name`, `date` | HTML-список ссылок на турниры |

Они возвращают `Content-Type: text/html`, а не JSON: это бэкенд
автодополнения, а не API. Единственный полноценный источник — HTML
страниц.

### Горизонт данных — скользящие 12 месяцев

Проверено на игроке с длинной карьерой (`66f1645`, 105 матчей): страница
содержит 13 недельных периодов с 15.09.2025 по 20.09.2026, ровно год.
`get_player_points` отдаёт те же 13 точек плюс якорь с даты регистрации
(2012-11-19) и при этом отстаёт от HTML примерно на месяц.

Более глубокой истории сайт не отдаёт ни в одном источнике. Сервер
сознательно не пытается это обойти.

### Ограничения, влияющие на дизайн

| Факт | Замер | Следствие |
| --- | --- | --- |
| Поиск режется на 500 строках, пагинации нет | «иванов» → ровно 500 строк, 485 КБ, 10 с | нужен флаг `truncated` |
| `/players/` без параметров отдаёт всё | 6.7 МБ, 7153 игрока, 17 с | пустое имя запрещено на уровне контракта |
| Сервер медленный | профиль игрока ~7 с, поиск 4–10 с | таймаут 30 с, запросы не параллелить |
| Поиск турниров режется на 20 строках | «кубок», «турнир», «а» → по 20 | нужен флаг `truncated` |
| `robots.txt` = `Disallow: /`, плюс `noindex` | — | сервер не должен уметь становиться краулером |

### Ключевая ловушка: сводка отстаёт на период

Сводная таблица на странице игрока («Обсчитано рейтингов / Сыграно
турниров / Статистика») не включает самый свежий период, а список «Все
игры» — включает. Проверено на двух игроках:

- `1c18ed8`: сводка «9 игр, 0-9», в списке 16 матчей за 2 турнира.
- `66f1645`: сводка «98 игр, 71-27, 72%», в списке 105 матчей.

Расхождение системное, не ошибка парсинга. Оно обязано быть описано в
докстринге `get_player`, иначе модель примет его за противоречие в
данных и начнёт «чинить» несуществующую проблему.

### Существующие решения

Поиск по GitHub (2026-09-22): MCP-сервера для r.ttw.ru **не существует**.
Два найденных MCP про настольный теннис не имеют отношения к источнику —
`whoisbe/pongbot-mcp` управляет роботом-подавальщиком по BLE,
`Justinandjohnson/omnipong-mcp` работает с omnipong.com.

Единственная prior art — `2FrogsStudio/spin-rally-bot`, Telegram-бот на
C#/AngleSharp, парсящий тот же сайт с 2023 года. Он решает более узкую
задачу (следит за изменением рейтинга) и достаёт всего три поля: ФИО,
рейтинг, позицию. Матчей, турниров и противостояний он не трогает, так
что переиспользовать нечего, но три вещи он подтверждает:

- его селекторы живы, проверено на текущей странице (раздел 6);
- `get_players_by_name` стабилен более трёх лет — это понижает риск
  отказа ajax из раздела 11;
- на неизвестный id сайт может ответить 404, а не только 200 с пустым
  профилем; обрабатываем оба случая.

Его клиент берёт текущий рейтинг из первой ячейки `.rating-rating-cell`,
а не из шапки, и это точнее нашего первоначального решения: шапка даёт
округлённое целое (`84`), ячейка — рейтинг последнего периода с двумя
знаками (`84.49`). Принято.

### Точность чисел различается по источникам

Рейтинг приходит целым в шапке профиля, в строках поиска и на странице
противостояния; с двумя знаками — в списке матчей, в периодах и в
таблице турнира. Сервер отдаёт то, что дал сайт, приводя к `float`, и не
пытается унифицировать точность.

## 3. Границы

Не делаем:

- кэш, локальную БД, архив снимков, фоновую синхронизацию;
- любую аналитику поверх данных (winrate по диапазонам, рейтинги
  «удобства» соперников, прогнозы) — это работа AI;
- обход ограничения в 12 месяцев;
- массовый обход сайта, перебор id, выгрузку всей базы;
- запись на сайт — сервер только читает.

Сознательно не делаем инструмент `get_rating_history` поверх
`get_player_points`: он отстаёт от HTML на месяц и добавляет к
`get_player` единственное новое поле — дату регистрации. Если понадобится,
добавляется отдельно и независимо.

## 4. Архитектура

```
ttw-mcp/
  ttw_mcp/
    __init__.py
    server.py     MCPServer, определения пяти инструментов
    client.py     HTTP-доступ: UA, таймаут, ретрай, сериализация
    parsers.py    чистые функции: HTML-строка -> dict
  tests/
    fixtures/     сохранённые страницы сайта
    test_parsers.py
    test_smoke.py живая сеть, отдельная метка
  pyproject.toml
  README.md
```

Стек: Python 3.11+, `mcp[cli]` >=2.0 (`MCPServer`, транспорт stdio),
`httpx`, `beautifulsoup4` на стандартном `html.parser`. `lxml` не берём: он тянет
сборку и ломается на свежих Python, а объёмы здесь такие, что скорость
парсера не важна.

### Разделение ответственности

`client.py` знает про сеть и ничего не знает про разметку. `parsers.py`
знает про разметку и ничего не знает про сеть: каждая функция принимает
строку HTML и возвращает словарь. `server.py` связывает их и описывает
контракты для модели.

Это разделение — главное решение дизайна. Разметка чужого сайта
единственная по-настоящему хрупкая часть системы, и чистые парсеры
позволяют тестировать её офлайн на сохранённых страницах, без сети и без
нагрузки на r.ttw.ru.

## 5. Контракты инструментов

Общие правила: даты наружу в ISO `YYYY-MM-DD` (сайт отдаёт
`DD.MM.YYYY`); числа — `float`/`int`, не строки; id игроков и турниров —
семизначные hex-строки, валидируются как `^[0-9a-f]{4,16}$`; русские
значения (ФИО, города, названия) не транслитерируются.

### `search_players(name: str, limit: int = 25)`

Источник: `GET /players/?player-name=<name>`.

`name` обязателен и непуст после `strip()`; пустой — ошибка
`InvalidInput`, запрос не отправляется (защита от выгрузки на 6.7 МБ).

Возвращает:

```json
{
  "total_found": 17,
  "truncated": false,
  "players": [
    {"id": "1c18ed8", "name": "<игрок A>",
     "city": "--, -Санкт-Петербург", "tournaments": 1, "games": 9,
     "wins": 0, "losses": 9, "rating": 85.0, "delta": -5.22,
     "date": "2026-09-14"}
  ]
}
```

`total_found` — сколько строк реально пришло со страницы; `players` —
первые `limit` из них. `truncated` истинно при `total_found == 500`
(потолок сайта) и означает, что результат неполон и запрос надо сузить.

### `get_player(player_id: str)`

Источник: `GET /players/?id=<player_id>`.

Возвращает: `name`, `player_id`, `city`, `current_rating`, `rank`;
`current_rating` берётся из первой ячейки `.rating-rating-cell` (рейтинг
последнего периода, два знака), а не из шапки, которая округляет до
целого;
объект `summary` (`rated_periods`, `tournaments_played`, `rating_min`,
`rating_max`, `rating_avg`, `games`, `wins`, `losses`, `win_pct`);
списки `periods` (`start`, `end`, `rating_after`, `delta`),
`tournaments` (`date`, `tournament_id`, `title`, `delta`), `best_wins`,
и `matches`:

```json
{"date": "2026-09-20", "tournament_id": "5f73688",
 "tournament_title": "Санкт Петербург. Турнир Энерджи Арена",
 "score_raw": "3:1", "score_for": 3, "score_against": 1, "result": "win",
 "opponent_id": "201fd1c", "opponent_name": "<игрок C>",
 "opponent_rating": 55.35, "delta": 1.41}
```

Техническую победу сайт пишет как `W:Тех` вместо счёта. Такой матч
возвращается наравне с остальными: `result` равен `walkover`, партии
`null`, исходная запись — в `score_raw`. Выбрасывать его нельзя: игра
состоялась, у неё есть соперник и дельта рейтинга.

Докстринг обязан сообщать модели две вещи: данные охватывают последние
12 месяцев, и `summary` отстаёт от `matches` на один недельный период
(раздел 2). `best_wins` часто пуст — это нормально, а не сбой.

### `get_head_to_head(player_id: str, opponent_id: str)`

Источник: `GET /players/?id=<player_id>&with=<opponent_id>`.

Возвращает `player` и `opponent` (каждый: `id`, `name`,
`current_rating`, `rank`), счёт противостояния (`wins`, `win_pct`,
`sets`, `sets_pct` — по каждой стороне) и `matches` с датой, турниром и
счётом.

Если очных встреч нет, страница отдаётся с нулями: это валидный ответ
`matches: []`, а не ошибка.

### `search_tournaments(name: str = "", date: str = "")`

Источник: `POST /wp-admin/admin-ajax.php`,
`action=get_tournaments_by_name`.

Хотя бы один из аргументов должен быть непуст. Возвращает
`{"total_found": N, "truncated": bool, "tournaments": [{"id": "...",
"title": "..."}]}`.

Эндпоинт режется ровно на 20 результатах: замерено на запросах «кубок»,
«турнир» и «а» — все три вернули по 20. `truncated` истинно при
`total_found == 20`, по той же схеме, что в `search_players`.

### `get_tournament(tournament_id: str)`

Источник: `GET /tournaments/?id=<tournament_id>`.

Возвращает метаданные (`title`, `date`, `address`, `organizers`,
`participants_count`, `games_count`, `info`), `standings`:

```json
{"place": 17, "player_id": "1c18ed8", "name": "<игрок A>",
 "city": "--, -Санкт-Петербург", "games": 9, "wins": 0, "losses": 9,
 "rating": 84.78, "delta": -5.22}
```

и `series` — другие турниры той же серии (`id`, `date`, `address`,
`organizers`, `participants`, `games`). Проверено: каждая строка серии
содержит ссылку с id, так что серия обходится без дополнительного поиска.

Страница турнира содержит только итоговую таблицу. Отдельных матчей
внутри турнира на ней нет — они доступны лишь со страниц участников.
Докстринг обязан это сообщать, иначе модель будет искать несуществующие
данные.

## 6. Парсеры

Разметка сайта построена на говорящих классах, парсинг идёт по ним, а не
по позициям ячеек:

| Данные | Селекторы |
| --- | --- |
| ФИО игрока (якорь) | `div.player-page h1 span` |
| Позиция в рейтинге | `div.header-position` |
| Матчи игрока | `.game-score-cell`, `.game-name-cell`, `.game-delta-cell` |
| Периоды рейтинга | `.rating-title-cell`, `.rating-rating-cell`, `.rating-delta-cell` |
| Турнир в списке игрока | `.game-tournament-name-cell`, `.game-tournament-delta-cell` |
| Таблица турнира | `.player-place-cell`, `.player-name-cell`, `.player-city-cell`, `.player-stat-cell`, `.player-rating-cell`, `.player-delta-cell` |
| Имя в строке поиска | `.player-name-cell a:not(:has(img))` — в ячейке две ссылки, первая на аватаре |
| Шапка турнира | `.tournament-date-cell`, `.tournament-address-cell`, `.tournament-organizer-cell`, `.tournament-num-players-cell`, `.tournament-num-games-cell`, `.tournament-info-cell` |
| Противостояние | `.compare-block-*`, `.compare-rating`, `.compare-position` |

Рейтинг соперника в списке матчей лежит внутри текста ссылки в скобках:
`<игрок C> (55.35)`. Парсер отделяет имя от рейтинга и
берёт id из `href`.

Знак дельты приходит и текстом (`+1.41`, `-0.50`), и классом
(`cell-upped` / `cell-downed`). Источник истины — текст; класс
используется только для проверки согласованности, и расхождение
логируется как предупреждение, не как ошибка.

## 7. Обработка ошибок

Потребитель — языковая модель, поэтому главное требование: **пустой
результат и сломанный парсер не должны выглядеть одинаково**. Модель,
получившая «0 матчей» вместо ошибки, уверенно построит на этом ложный
вывод.

| Ситуация | Поведение |
| --- | --- |
| Разметка изменилась, обязательный блок не найден | исключение `ParseError` с именем парсера и селектора |
| Несуществующий id | сайт отдаёт либо 404, либо 200 с пустым профилем; оба случая дают явный `not_found` |
| Нет матчей у нового игрока | валидный ответ с пустым списком, не ошибка |
| Таймаут или сетевой сбой | один повтор, затем `UpstreamError` с указанием URL и таймаута |
| HTTP 4xx/5xx | `UpstreamError` с кодом, без повтора |
| Пустое имя в `search_players` | `InvalidInput`, запрос не отправляется |
| Достигнут потолок в 500 строк | успешный ответ с `truncated: true` |

Различие «пусто» и «сломалось» проводится по обязательным якорям: для
профиля — `div.player-page h1 span`, для турнира — шапка
`.tournament-date-cell`, для противостояния — блок `.compare-title`. Нет якоря — `ParseError`; есть
якорь и нет строк — честный пустой список.

## 8. Отношение к сайту

Сайт просит не обходить себя автоматически (`robots.txt: Disallow: /`),
работает на PHP 5.6 и отвечает за 4–17 секунд. Сервер рассчитан на
интерактивное личное использование и не должен уметь становиться
краулером:

- честный User-Agent, идентифицирующий инструмент;
- таймаут 30 с, не более одного повтора;
- запросы сериализованы, без параллельных пачек;
- нет инструмента, обходящего список игроков или перебирающего id;
- `search_players` не работает без имени.

Если когда-нибудь понадобится объёмная выгрузка — это разговор с
администрацией (`ttw-r@mail.ru`), а не задача этого сервера.

## 9. Тестирование

Разработка по TDD: сначала тест парсера на фикстуре, затем парсер.

**Тесты парсеров** (основной объём) работают офлайн на сохранённых
страницах в `tests/fixtures/`. Стартовый набор уже собран в ходе
разведки и покрывает содержательно разные случаи:

- профиль новичка (`1c18ed8`): 2 периода, 16 матчей, пустые «лучшие
  победы», расхождение сводки и списка;
- профиль ветерана (`66f1645`): 13 периодов, 105 матчей, полный
  12-месячный горизонт;
- поиск с несколькими результатами (`тренкин`) и поиск на потолке
  (`иванов`, 500 строк);
- противостояние с одним матчем (`1c18ed8` × `17828c3`);
- турнир (`6ad412a`): 17 участников, серия из 6 турниров.

Каждый парсер проверяется на успешном разборе, на честно пустом
результате и на повреждённом HTML, где обязан подняться `ParseError`.

**Smoke-тест** с живой сетью — один, помечен так, чтобы не запускаться в
обычном прогоне. Он проверяет, что разметка сайта всё ещё совпадает с
фикстурами, и является единственным способом заметить, что сайт
переехал.

## 10. Установка

Проект ставится через `uv`. Регистрация в Claude Code:

```json
{
  "mcpServers": {
    "ttw": {
      "type": "stdio",
      "command": "uv",
      "args": ["--directory", "/Users/lappi/Work/ai/ttw-mcp", "run", "ttw-mcp"]
    }
  }
}
```

Конфигурации и секретов сервер не требует: источник публичный, авторизации
нет.

## 11. Риски

**Разметка сайта изменится.** Главный риск: парсинг HTML — единственный
доступный способ. Смягчение: селекторы по классам, а не по позициям;
`ParseError` вместо тихой пустоты; smoke-тест как детектор.

**Сайт может закрыть `admin-ajax`.** На нём держится
`search_tournaments`. Риск ниже, чем казался: `spin-rally-bot`
использует эти же действия с 2023 года и продолжает работать.
Смягчение: поиск турниров при необходимости переносится на разбор
страницы `/tournaments/`; остальные четыре инструмента от ajax не
зависят.

**Однофамильцы.** Поиск по «калугин» даёт десятки людей, среди них
полные тёзки, различимые лишь пометками вроде «левая». Разрешение
неоднозначности оставлено модели: инструмент отдаёт город, рейтинг и
статистику, которых для выбора достаточно.
